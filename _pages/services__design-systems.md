# Design system services: one set of parts for every team and product

Your teams build screens faster from documented components in Figma and code. Our design system services keep the library current as the product grows.

## Selected design system work {#selected-work}

### Gold Image Printing: shared parts first, then two products drawn from them

Gold Image Printing's customers order print online, and its staff turn each order into work in a separate production system. We designed the shared parts before the screens and used them on both sides, so a recurring control looks and behaves the same wherever someone meets it.

[Read the Gold Image Printing case](/case-studies/gold-image-printing-web-to-print-erp-modernisation)

### Auxentios: core screens first, then the rules for the rest

Auxentios' industrial quoting product was planned to run to more than 200 screens. We designed the core experiences, then turned what kept repeating into components, variants, design tokens and layout rules. Its own product and engineering teams can design further screens to match.

[Read the Auxentios case](/case-studies/auxentios-cpq-product-mvp-design)

### Benchmark Gensuite: shared components first, across every application

In Benchmark Gensuite's suite, one change to a shared component reaches every application. We started at that layer, tested the components inside a high-use control, and our coded prototypes gave Benchmark's engineers a component direction for their move to Bootstrap 5.3.

[Read the Benchmark Gensuite case](/case-studies/benchmark-gensuite-enterprise-suite-modernisation)

## What you get from our design system services {#what-you-get}

Buy the work as one programme, or start with the part that hurts most.

- **Colours, type and spacing named by use:** colour, type and spacing tokens that give every product one look, named so people and AI coding tools pick the right one.

- **Components in Figma and in code,** each with all its states, shown in Storybook and released together, so design and code describe the same button.

- **Documentation in plain words:** each component's options and states, and when it belongs on a screen.

- **A first release:** tried on a real part of your product before you sign it off.

- **A way to change the system:** who owns the system, how teams contribute and raise exceptions, how releases go out, and how you will see whether teams use it.

**Who does the work.** The system is led and designed by a senior product designer, and an account lead keeps the project on track. Design engineers build the coded components to fit your frontend, working inside your team's Figma files, code and release routine.

**What we need from you.** The screens, Figma files and code your teams use today, and where they copy or override shared parts. We also need the product, design and frontend leads who will own the result.

**Where our part stops.** After the first release, your team runs contributions, exceptions and releases, with us alongside when you want the help. Your codebase and your product decisions stay yours.

## Worked example: one status label, everywhere it appears {#status-example}

A "Partly complete" status works only if every part of the system agrees on it.

| Where | What has to be true | What goes wrong if it isn't |
|---|---|---|
| Meaning | Some of the work is done; some still needs action | Teams use the same label for different things |
| Design | Shown with text and an icon as well as colour | The status looks different in every product |
| Figma | Ready-made versions for the label, detail and next step | Designers copy and edit the component to fill gaps |
| Code | The component supports exactly those versions | Code allows combinations the product never meant |
| Guidance | Examples of when to use it, and when to avoid it | Teams guess from a single example |

## Where an enterprise design system gets hard {#hard-parts}

**Keeping teams on the system after launch.** A library nobody uses fails quietly, one local copy at a time. We plan for year two, so the system has an owner and a way to change after the first release.

Example: [Ryzeo's](/case-studies/ryzeo-marketing-automation-ux-revamp) reporting redesign came with documented components, so later work can follow one set of rules for filters, states and data.

**Rules that people and AI coding tools can follow.** AI coding tools now draft many screens, and they are only as good as the system they draw on. We name every token by its meaning and describe each component's options, states and use in plain words, in Figma, code and documentation.

Example: [Matter](/matter-design-system), the free Figma design system we made and published, shows how we name tokens for their purpose and build components from smaller parts.

## How a design system project runs with Tcules {#how-it-runs}

1. **Start from the product** your teams ship today, and where they copy or override shared parts.

2. **Agree scope and owners:** what every product shares, what stays with one product, and who approves a change.

3. **Build the first release on a real screen,** starting with the component families your products use most.

4. **Release design and code together,** as one version with notes on what changed.

5. **Hand over the way to change it,** so your team runs contributions, exceptions and releases.

## Questions buyers ask about design system services {#faq}

### Do you code the components as well as design them?

Yes. Tcules designs the system in Figma and builds the coded components, Storybook stories and documentation to fit your frontend. Both release together, so design and code stay in step.

### Can you fix our existing system instead of starting again?

Yes. Tcules reviews your components and how teams use them, then repairs or extends what needs it. If replacing a part is the better decision, we say so.

### Should Storybook be our single source of truth?

Storybook should own how components behave in code. Figma, your product rules and your release process own other parts, and Tcules makes clear which source answers which question for your teams.

### How do we know if teams are using the system?

Three measures track adoption: how often teams pick shared components over local copies, how often they override them and how far migration has got. Tcules sets these up with you from your design and code.

### Can you build a design system for multiple brands?

Yes. Where brands share one codebase, we build one set of components with a theme layer that changes colour and type for each brand. A suite works the same way: shared foundations under every product, and room for each one's own workflows.

### Do we need a design system consultant or an agency?

Design system consulting suits a team that will build the system itself and wants an experienced view on scope and structure. A studio suits a team that also needs the components designed, coded and documented. Our guide covers [when to hire a design system consultant, and what they should deliver](/insights/when-to-hire-a-design-system-consultant).

### How much does a design system cost?

The cost depends on how many products the system serves, how much already exists and how many component families the first release needs. Tcules prices the work up front, once that scope is agreed. [How pricing works](/how-we-work#engagement-shapes)
