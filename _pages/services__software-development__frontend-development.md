## What you get from our frontend development services {#scope}

The running interface of your product, built from approved designs inside your own codebase, for a new release or a live product.

- **Screens and components.** Built with your design system, or extending it through your team's contribution process.

- **Every state with each feature.** Loading, empty, error and permission states go in as the feature is built and are tried on realistic data.

- **API connections.** Real responses, slow ones and failed ones, each with a message the user understands.

- **Accessibility.** Keyboard use, focus order, labels and screen-reader behaviour in each component. Our guide to [designing products for older and disabled people](/insights/guides/inclusive-product-design-for-older-and-disabled-people) sets out who these checks serve.

- **Performance.** Load times checked in the browsers your customers use.

- **Design review.** A designer checks the working screens against the design at each screen size, with real data, before release, and the team fixes the differences.

- **Tests and release.** Automated tests for the tasks customers rely on, pull requests in your review queue, release notes and release alongside your team.

**Who does the work.** Our developers build, with designers reviewing the screens as they take shape and an account lead keeping it running. A senior engineer reviews every change before it reaches your codebase. They learn your conventions, components, tests and release process first, so new code fits the application you already have.

**What we need from you.** The designs, or a brief our designers can start from. Access to your codebase, its tests and your release process, and someone who can sign off a screen.

**Where our part stops.** Code review, release and handover follow your process, so your engineers pick up where we stop. A hard interaction nobody has solved yet belongs to [Design Engineering](/services/design-engineering).

## Empty, slow and error screens, built to match the design {#states}

The design file shows each screen at its best. Your users meet the rest: long names, empty lists, slow responses, expired sessions and a button their role cannot use, often all at once.

| Situation | What we build |
|---|---|
| **Waiting** | Loading states, background work that keeps screens usable, progress bars |
| **Nothing there yet** | Empty states that explain what to do first |
| **Something failed** | Clear error messages, saved input and a way to retry |
| **Different users** | Screens that change with roles and permissions |
| **Awkward content** | Long names, missing images, partial data and stale records |
| **Every screen size** | Layouts that work from a phone to a wide monitor |

These go in with the feature from the start, so real data meets a finished screen. Tests cover the tasks customers rely on, because a release that breaks a screen nobody touched costs trust before anyone files a ticket. Our article on [what quiet interface regressions cost before anyone complains](/insights/silent-ui-regression-debt-erodes-adoption-before-it-shows) explains why.

## Questions about frontend and React development {#faq}

### What is the difference between frontend development and design engineering?

Frontend development owns the running interface: each screen with its data connections, tests and releases. [Design Engineering](/services/design-engineering) takes the parts whose behaviour is still open, works them out in code and builds them to production standard. Many projects use both.

### How do you check the build matches the design?

A designer reviews the working screens against the design before each release, with real data and at each screen size, and the team fixes what they find. For a one-off check of a release your own team built, see [Implementation QA](/services/design-engineering/implementation-qa).

### Can you work inside our existing React frontend?

Yes. Our code follows the patterns, components and tests already in your application, so no parallel version grows up beside it. Your engineers see our pull requests in the same queue as each other's and review them the same way.

### Should we outsource React development?

It suits teams whose engineers are stretched or whose interface keeps drifting from the design. It works best on a bounded part of the product, with shared code review and designers involved, which is how we run it.

### How do you make a frontend accessible?

We build keyboard use, focus order, labels and screen-reader behaviour into each component as it is made, then check them again on the finished screens. Colour contrast and text size are checked against your design system, and anything that falls short goes on the fix list before release.
