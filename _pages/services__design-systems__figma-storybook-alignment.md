We align Figma and Storybook, then add checks that flag the next mismatch before it reaches your product or slows a handoff.

## What you get from Figma and Storybook alignment {#what-you-get}

Your Figma library and Storybook, the catalogue of your coded components, made to agree on colours, options, states and names, family by family.

- **A side-by-side map of Figma and code.** How Figma and code line up, with every gap marked against six questions: colours and spacing, options, cases, behaviour, who decides and checks.

- **The gaps that matter, fixed.** In Figma, in code or in both, with design tokens carrying the same names from one to the other.

- **A Storybook entry for each case.** Loading, empty, error, disabled and validation, so designers and developers look at the same set.

- **Behaviour written where designers can see it.** Keyboard, focus and screen-size behaviour that exists only in the running component, described beside the Figma component.

- **A written rule for who decides.** For each family, which side leads when the two disagree.

- **Checks and release notes.** Checks that flag when design and code stop matching, and notes that explain changes that break things.

**Who does the work.** A design engineer reads your code and Storybook while a senior designer works through the Figma library, and the two of them map each family together. An account lead looks after timing and scope.

**What we need from you.** A Figma library and coded components, access to your repository or at least a running Storybook, and one person from design and one from frontend who can make decisions. A library someone else built is fine, because we map what exists before changing anything.

**Where our part stops.** We align one family at a time, and your team owns both libraries throughout. If one side is missing or both need starting again, that is [Design System Implementation](/services/design-systems/design-system-implementation).

## One component, mapped across Figma and code {#mapping}

Using Storybook as single source of truth works for some questions, and Figma is the better authority for others, so we write the answer down for each component family.

**Figma leads on appearance and use.** How a component looks, where it belongs and how screens are composed.

**Code leads on behaviour.** The options a component accepts, how it responds in the browser, and keyboard and screen-reader behaviour.

**Your product decides what a label means.** What a status, action or label means to your users, whichever tool shows it.

That matters more now that AI coding tools read Figma files and component code to write new screens. A tool that finds two versions of the same button copies whichever it meets first.

Here is what one row of the map looks like for a single button.

*Illustration, not client work*

A primary button in a SaaS product's design system, checked against the six questions.

| Question | In Figma | In code | What we agree |
|---|---|---|---|
| Colours | "Primary", a lighter blue | "primary", a darker blue | One name, one value, set from the code side |
| Options | Small, medium and large; a "ghost" style | Small and medium only | Large is built; ghost is retired from Figma |
| Cases | Default, hover and disabled | Adds loading and focus | Loading and focus are drawn in Figma |
| Behaviour | Nothing recorded | Ignores repeat clicks while loading | Written into the Storybook entry and the Figma description |
| Who decides | Appearance | Behaviour and options | Recorded for the whole button family |
| Checks | None | None | A check flags any option that exists on one side only |

## Figma and Storybook alignment FAQs {#faq}

### How do we keep Figma and Storybook components in sync?

Give each value and component the same name in both, release them together, and add checks that flag a mismatch. Tcules sets up all three, starting with the component family that drifts most.

### Should Figma and Storybook match exactly?

They should match wherever they describe the same thing: colours, variants, states and names. Some behaviour exists only in the running component, and some Figma content is guidance for designers. Those differences should be deliberate and written down.

### Can Figma and Storybook sync be automated?

Much of it can. Checks on colour values, component names and state coverage run automatically. Whether a difference is a mistake or a sensible choice takes a person who knows the product, and Tcules makes that decision with you.

### Do you set up Figma Code Connect?

Yes. Code Connect shows developers the real code for each Figma component, inside Figma. We set it up once the two sides match, so the link points to the right version of each component.

### What if we use a different tool from Storybook?

Then we align Figma with that tool. The method stays the same: map colours, variants, states and behaviour, and agree who decides. You can also run a quick self-check with our [Figma to Storybook Fidelity Checklist](/tools/figma-storybook-fidelity-checklist).
